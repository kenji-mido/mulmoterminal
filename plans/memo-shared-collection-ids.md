# メモ: 共有コレクションの識別子と置き場所

**状態**: **本文への反映は完了**（2026-08-11）。
[`feat-shareable-collections.md`](./feat-shareable-collections.md) と
[`shared-collection-flow.md`](./shared-collection-flow.md) が正で、このメモは
**決定の理由**の記録として残す（本文は「何をするか」、ここは「なぜそう決めたか」）。
**日付**: 2026-08-11
**きっかけ**: mulmoclaude #2867 のレビューが「別アプリの同名コレクションが 1 つの一覧で
衝突して片方が黙って消える」を指摘したこと。議論はそこから、**誰がどこから使うのか**まで
広がった。

---

## 前提が 1 つ変わった（これが他の全部を決めた）

**publish されたアプリを他の人は Web サイトから使う。** 招待された人が自分の
MulmoTerminal でそのコレクションを扱う、という形は取らない。

これで「ホストが他アプリのコレクションを自分の一覧に出す」必要が消え、
**衝突そのものが起きなくなった**（下記）。

---

## 決定 1 — `cid` は slug のまま（UUID にしない）

**一度 UUID で実装したが、前提が変わったので戻す。**

衝突が起きないことは、次の 3 つで保証される:

1. **ホストは自分のリポジトリのコレクションしか見ない**（他アプリを購読しない）
2. **1 フォルダ 1 アプリ**（D1）
3. MulmoTerminal は N 個の root を serve するが、**1 セッションが見る root は 1 つ**

slug はフォルダ内のディレクトリ名なので、**ファイルシステムが一意性を保証する**。
`manageCollection` が単一の文字列で引く形も、そのままで曖昧さがない。

**残る弱点（受容する）**:
- コレクションを削除して同じ名前で作り直すと、**古いレコードの残骸を引き継ぐ**
  （`apps/{aid}` を消しても `items` は残る）
- ディレクトリを rename すると同一性が変わり、レコードが古いパスに取り残される
  （実際には誰も rename しない。利用者に見えるのは `title`）

**実装順 3 の決定 7「`cid` は常に collection の slug」は維持**。

---

## 決定 2 — `aid` は UUID

cid とは**名前空間の性質が違う**。

`apps/{aid}` は**全ユーザー共通**で、ルールの `allow create` が要求するのは「自分を
オーナーと名乗ること」だけ。したがって人間可読な aid には:

- **早い者勝ち**。推測しやすい aid は先回りして押さえられる
- **宣言〜publish の窓**: `app.json` に aid が入るのは**アプリを宣言した時点**
  （publish ではない — aid が無いとコレクションが保存できない）。`apps/{aid}` が
  できるのは publish。その間 aid は平文でリポジトリにあり、まだ誰のものでもない
- **空いているか調べられない**（`apps/{aid}` は読み取りが絞られている）
- **削除で窓が開き直す**（プラン既述の「空いた aid を先に拾った他人が owner になれる」）

cid はアプリの中に閉じていて、かつフォルダが一意性を保証するので、この 4 つが無い。
**だから aid だけ UUID**。

**生成はコード**（LLM に発明させない）。**`app.json` を書くときに生成する** — publish は
aid を作らない。UUID は取り合いが無いので早く決めて損が無く、遅らせると `putSchema` が
共有コレクションを拒否する。**publish まで遅れるのは slug の確保だけ**（決定 3）。

---

## 決定 3 — URL 用の slug は別に持ち、deploy が予約して publish が公開する

同一性（aid）と名前（URL）を分ける。**取り合いの対象を、捨てても痛くない方に移す。**

- **LLM が `app.json` に希望の slug を書く**
- **deploy が予約し、publish が公開する**（決定 8 で分割）。衝突していたら**後ろに番号**
  （`sakura-hair` → `sakura-hair-2`）
- **一度確保したら再生成しない**（URL は人が配るもの）
- 確保した slug は `app.json` に書き戻す

逆引きが要る:

```text
appSlugs/sakura-hair  →  { aid: "3f2b8c1a-…" }
```

- `allow read: if resource.data.published == true`（公開ページは未ログインで引くが、
  **公開前は誰も辿れない** — 決定 8）
- `allow create` は「その aid のオーナーであること」を `get(apps/{aid})` で確認
  （したがって **`apps/{aid}` を書いてから予約する**）
- `allow update` はオーナーのみ、かつ `aid` の付け替え禁止（publish / unpublish が
  `published` を反転させるので、無いと既定の deny で失敗する）
- 確保は `create`（原子的な create-if-absent）。継ぎ目に既にある

**これは今やる**（ルールの 2 回目の cross-repo デプロイを含む）。

---

## 決定 4 — 共有コレクションは MulmoTerminal のプロジェクトフォルダにだけ置ける

**反映済み**: D5。

**D5 として最初から決まっていたが、未実装で、しかも実装は逆の状態にある** —
現時点で Firestore に繋がっている唯一のホストが MulmoClaude（サポート対象外の方）。

- **MulmoTerminal に Firestore を繋ぐ**（本来のホスト。`setFirestoreAccessor` を呼ぶ）
- **MulmoClaude のワークスペースでは拒否する**。コードで拒否する（黙って成立させない）。
  ホストが「この root は共有コレクションを持てない」と宣言する形

理由: ワークスペースは雑多な置き場（`47news` `blood-tests` `clients` …）で、
そこに `app.json` を 1 つ置くと**全部が同じ名簿になる**。「顧客リストの共有相手が
血液検査の結果も見える」形になる。

---

## 決定 5 — 1 フォルダに共有と非共有を混ぜない

**反映済み**: D5b（新設）。

衝突対策ではなく、**フォルダの性格を 1 つに定める**ため。

`app.json` があるフォルダのコレクションは、すべて firestore ストレージであること。

**代償**: そのリポジトリに「共有しないメモ」や下書きコレクションを置けなくなる。

---

## 決定 6 — 1 フォルダ 1 アプリで通す（D1 のまま）

**反映済み**: D1 に追記。

名簿を分けたければリポジトリを分ける。monorepo で名簿を分ける形は取らない。

---

## 決定 7 — Web の入口は 2 つ。招待の前に本物で試せるようにする

**普通のアプリは、招待や公開の前にテストする。** その段階が無かった — publish が
「Firestore に出す」と「本番にする」を兼ねていたので、動作確認の手段が「先に公開する」
しかなかった。

**分けるのはデータではなく、誰に見えるか。**

```text
/{slug}           公開の顔。未サインインでも読める
/staging/{aid}    名簿の人の入口。slug を経由しない
```

- **検証用に別の aid は立てない。** テストデータが本番に持ち越せず、
  「検証用のアプリでは動いたのに本番にそのデータが無い」を作る。aid もレコードのツリーも 1 つのまま
- **Firestore 側に足すものは無い。** 認可はルールが持っている（`public.enabled` が
  false なら名簿の外の人は何も読めない）。足りないのは `appSlugs` を引かない経路だけ
- **公開後も消えない。** お客さんは `/{slug}`、スタッフは `/staging/{aid}`
- **名前は `staging`**（決定 9）。その入口が読むドキュメント
  （`apps/{aid}/staging/{cid}`）と一致する。開発環境ではない — データは 1 つで、
  staging なのはスキーマとビューだけ

**反映済み**: D10 として本文に追加。実装順 9 が `/staging/{aid}`、12 が `/{slug}`。

---

## 決定 8 — `deploy` と `publish` を分ける

決定 7 だけでは漏れる。`apps/{aid}/config/*` は `allow read: if true` なので、
**テストのために反映しただけでアプリ名が世界に読める**。さらに `appSlugs/{slug}` が
最初から引けると、**人間可読な slug を当てるだけで aid が手に入り**、`/staging/{aid}` の
秘匿が消える。

| | 何を書くか | 危険度 |
|---|---|---|
| **deploy** | 名簿の人しか読めないもの（`apps/{aid}`、`collections/{cid}`） | 常に安全。何度でも |
| **publish** | 世界に読めるもの（`config/public`、`appSlugs/{slug}` の公開） | 唯一の危険な操作 |

- `config/public` は **publish するまで存在しない**（「名前だけ書かない」は不要）
- **slug の予約は deploy、公開は publish。** `appSlugs/{slug}` に `published: false` を持たせ、
  `allow read: if resource.data.published == true`。早く押さえられて、公開まで誰も辿れない。
  `get()` が増えないので式数も増えない
- **`unpublish` が表現できる**（`published` を戻し `config/public` を消す）
- **門番は deploy 側**（拒否条件・ライブレコード事前検証）。publish 側は公開の可否だけ
- `/staging/{aid}` は **deploy だけで動く** — テストと招待は publish 抜きで完結する

**反映済み**: D10 に追記。実装順 7a。決定 3 の「publish が確保」は「deploy が予約し
publish が公開する」に読み替える。

---

## 決定 9 — staging（スキーマとビューの草稿）

決定 8 の deploy / publish 分割では足りなかった。**公開ページはスキーマを
`apps/{aid}/collections/{cid}` から直接読む**（`schemaRead` に `publicRead` が入っている）ので、
スキーマを deploy が書く形だと**公開済みのアプリでは deploy した瞬間にビューが差し替わる**。
「テストのために deploy した」が本番の変更になっていた。

```text
apps/{aid}/staging/{cid}       deploy が書く。名簿の人だけ。/staging/{aid} が描画に使う
apps/{aid}/collections/{cid}   publish が昇格させる。公開ページが読む
```

**staging に載るのは**: スキーマとビュー（`publishedSchema`）、そのコレクションの
**ルール設定**、`participantRead` に入るかどうか、記名（`deployedAt` / `deployedBy` /
`deployedCommit`）。ルール設定まで載せるのは、ルールが**公開の書き込みを判定するときに
読む**から — deploy で着地させると、スキーマは staging のまま公開の挙動だけが変わる。
**名簿は載らない**（招待は deploy で即座に効く）。

**書き方は `set`（置換）**。merge は削除できないので、メンバー削除も非公開化もできない。
相手の操作が持つフィールドは現在値を持ち越す。`public` は**最後に単独で**書く（fail closed）。

- **別ドキュメントにする。** ルールはフィールド単位で隠せないので、公開ページが読める
  ドキュメントに草稿を入れれば草稿も読まれる
- **データは共有したまま。** staging はスキーマとビューの置き場所で、レコードのツリーは 1 つ。
  `/staging/{aid}` で試したレコードはそのまま本番のレコード
- **主に変わるのはビュー。** スキーマ変更は**後方互換である限りエラーにならない** —
  公開中の古いスキーマは、増えたフィールドを知らないだけで既存レコードを読み続けられる。
  後方互換でない変更は publish のライブレコード事前検証が止める
- `unpublish` は `collections/{cid}` を消さない（公開でなければ誰も読めない）
- **ルール追加**は `appSlugs` と同じ 2 回目の cross-repo デプロイに相乗りさせる

**反映済み**: D10 の staging 節、D4（成果物が 2 段）、実装順 7c。

## 落とすもの

**実装順 4（discovery の 2 ソース化 + skill materialize）を丸ごと落とす。**

- **mulmoclaude #2867 を閉じる**（購読 discovery）
- skill materialize も不要（説明文を届ける先が無い — 他の人は Web から使う）

**ただし #2867 に混ざっている購読と無関係な修正は救出する**:
- `public.submit[cid].createFields` が**空を許す**（「ID だけの投稿」= 出席・投票の形）。
  #2868 のレビューから引き継いだもの

**`memberEmails` は残る。** ホストが引かなくなっても、**Web ページが「自分が参加して
いるアプリ」を引く**のに同じクエリを使う。ルールも `membersConsistent()` で一致を要求する。
理由が「ホストの discovery のため」から「**Web クライアントのため**」に変わるだけ。

## 前提として確認したこと
