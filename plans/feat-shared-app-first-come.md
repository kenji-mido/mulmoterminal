# 共有アプリ: 先着枠つき予約（解禁時刻・申込み順・定員をビューで出す）

**状態**: 設計のみ。実装は未着手。2026-08-12 の議論から。
全体設計は [`feat-shareable-collections.md`](./feat-shareable-collections.md)、
行スコープの承認は [`feat-shared-app-assignee-role.md`](./feat-shared-app-assignee-role.md)。

**追加する宣言は 2 つだけ**（`stampField` と相対的な解禁時刻）で、定員と繰り上げは
**カスタムビュー側で解く**。Functions は要らない。

---

## 作れるようにしたいもの

> スポーツジムのクラス。定員 8 名。**3 日前の朝 8 時**に申込みが解禁され、先着 8 名まで確定、
> さらに **2 名まで待機**に入れる。キャンセルが出たら**自動的に繰り上がる**。

現状の判定:

| 要件 | 今 |
|---|---|
| 1人1枠 | **できる**。`idFrom: "auth.uid+field"` + `idField: "classId"` |
| 3日前の朝8時に解禁 | できない。`window` は絶対時刻 1 個でコレクション全体に効く |
| 先着 8 名で締切 | **ルールでは原理的にできない**（下記） |
| 待機 2 名・キャンセルで自動繰り上げ | 副作用なのでルールにはできない |

---

## 中心となる転換 — 定員は「状態」ではなく「順位」

Firestore のセキュリティルールは**件数を数えられない**。クエリも集計も書けず、判断材料は
「今書こうとしている 1 件」と `get()` で名指しした少数のドキュメントだけ。だから
`maxCount: 8` という宣言はどう作っても実現できない。

そこで**定員を保存された状態にするのをやめ、申込み順の順位から導出する**。

- 申込み順に並べて 1〜8 番目が確定、9〜10 番目が待機、11 番目以降は待機 3 番…
- **繰り上げが自動になるのではなく、繰り上げという操作が消える。** 3 番目がキャンセルすると
  9 番目は**書き込みゼロで**8 番目になる。トリガも待機列の管理もいらない。
- **競合が消える。** 8 時ちょうどに 30 人が殺到しても、全員が自分のドキュメントを 1 件書くだけ。
  奪い合うカウンタが無いので、トランザクションも再試行も要らない。**カウンタ方式より正しさの
  面で優れている**（分散カウンタは「ルールで守れない不変条件をクライアントの善意に預ける」形に
  なるが、こちらは守るべき不変条件がそもそも存在しない）。
- 溢れても壊れない。11 人目は「待機 3 番」という意味のある行になるだけ。

キャンセルは delete ではなく `status: "cancelled"` にして、ビューが除外して順位を詰める。
誰がいつ抜けたかが残り、`transitions` の状態機械も効く。

## 追加 1: `stampField` — 申込み順を偽装させない

順位が真実の源になるので、**`createdAt` をクライアントが書けると過去の時刻を書いて列に
割り込める**。`idFrom: "auth.uid+field"` は複数申込みを防ぐが、時刻の偽装は防がない。
`validate.keyFields` は値を宣言された集合に固定するものなので、これも使えない。

ルールで書けば 1 行:

```
request.resource.data[s.stampField] == request.time
```

submit 宣言にキーを 1 つ足す:

```json
"public": { "submit": { "bookings": {
  "auth": "verifiedEmail", "emailField": "memberEmail",
  "idFrom": "auth.uid+field", "idField": "classId",
  "stampField": "createdAt",
  "createFields": ["classId", "memberEmail", "memberName", "createdAt", "status"],
  "initialStatus": "requested"
} } }
```

クライアントは `serverTimestamp()` を書く。**先着・締切・監査のいずれにも効く汎用機構**で、
この計画の中でいちばん再利用が効く追加。

**`stampField` は create でのみ検査する。** update でも同じ検査をすると、`selfUpdate` で
キャンセルするときに `createdAt` を書き換えねばならなくなる（= 順位が変わる）。update 側は
「`createdAt` が変わっていないこと」を見るのが正しい。

## 追加 2: 解禁時刻をレコードから読む

`inWindow` が読む `window.from/until` は submit 宣言に 1 個、つまりコレクション全体に 1 つの窓
しかない。「各クラスの 3 日前の 8 時」は**レコードごとの相対時刻**なので表現できない。

**ルールで日付計算をしない。** タイムゾーンが入り、`request.time` は UTC で、ルールには
まともな日付演算が無い。代わりに**クラスのレコードに `opensAt`（epoch millis）を事前計算して
持たせ、ルールはそれを読んで比べるだけ**にする。既存の `window` が publish 時に ISO を
epoch millis に落としているのと同じ思想（ルールは文字列を強制変換しないので、ISO が届くと
型エラーで fail closed する）。

```json
"window": { "fromField": { "ref": "classId", "in": "classes", "field": "opensAt" } }
```

- 参照先を読む `get()` が 1 件増える。`gateOn` が `session/current` を読んでいるのと同じ形で
  前例がある。文書アクセス上限（単一文書リクエストで 10 件）には収まる。
- `opensAt` を計算するのは**クラスを登録する側**（オーナー、またはスケジュールを作るスキル）。
  「3 日前の 8 時」というルールはアプリの業務知識であって、ルールに持たせるものではない。
- `ref` の値は参照先の主キー slug なので、`get()` のパスは
  `apps/{aid}/collections/{in}/items/{data[ref]}`。**`in` は宣言で固定**する（レコードの値から
  コレクション名を組み立てさせない）。
- 参照先が無い / `opensAt` が無い場合は **fail closed**（申込めない）。`in` ガードを先に書く。

## ビューの責務

カスタムビュー（スキーマの `views`、`views/*.html`、LLM が書く HTML）が、読み取れた行から:

1. `status != "cancelled"` を `createdAt` 昇順に並べる
2. 先頭 8 件を「確定」、次の 2 件を「待機 1・2」、それ以降を「待機 3…」として描く
3. 自分の行を強調して「あなたは待機 1 番です」と出す

**ビューは強制ではない。** 9 番目の人が現場に来ることは止められない。ただし順位方式では
データが壊れないので、これは「システムの不整合」ではなく運用の話に落ちる。定員が法的・
課金的に厳格なアプリには向かない（そのときは Functions）。

「8」と「2」をどこに書くかは決めの問題で、**スキーマの `views[].config` に持たせる**のが素直
（ルールは読まないので、`collections[cid]` に置く理由がない）。

## 最大の制約 — 読めない行は数えられない

**ビューは読める行からしか順位を計算できない。**

| 誰が使うか | 順位が見えるか | 代償 |
|---|---|---|
| 会員が名簿に載る（`participant` + `peerVisibility: "public"`） | **見える** | **参加者全員の名前が互いに見える** |
| 名簿に載らない一般公開（`public.submit` のみ） | **見えない**（自分の行しか読めない） | 自分が何番目かも分からない |

ジムは会員制なので前者で自然だが、「誰が来るか」が全員に見えることは**受け入れる前提**であり、
アプリを作る前に利用者に確認すべき事項。避けたいなら、順位だけを載せた集計ドキュメントを
オーナー側で書いて公開する（既存の `aggregate` の考え方）ことになり、**即時ではなくなる** —
先着アプリとしては価値が大きく落ちるので、この計画では採らない。

---

## 残る穴 — 繰り上げは通知できない

**繰り上げは書き込みを伴わないので、通知の起点が無い。** `mail` キューはレコードの遷移を
トリガに宛先と本文をレコードから再導出する仕組みなので、何も書かれない繰り上げには反応しない。

- 画面を開けば「繰り上がりました」と出せる
- **メールは飛ばない**

キャンセルした人の行には書き込みがあるので、そこを起点に「このクラスの待機者に通知」を積む
形は考えられるが、**宛先が別のレコードの人**になるため `mail` の安全性の前提（宛先はその
レコードから再導出される）を崩す。設計ノートが警戒しているスパム中継の経路そのものなので、
**通知が要るなら Functions**、と割り切る。この計画には含めない。

**SKILL に書くべき制約**: 先着アプリを作るとき、繰り上げ通知は無いことを最初に利用者へ言う。
作り終わってから言うのでは遅い。

### publish 時に拒否すること（`publishChecks`）

- `stampField` が実在する**保存フィールド**で、型が `datetime` であること。計算フィールドは
  ルールが見る生レコードに存在しないので、指定すると**永久に fail closed** する
  （`completionField` に同趣旨の拒否メッセージがある。同じ罠）。
- `stampField` は `createFields` に**含まれていなければならない**。`hasOnly(createFields)` に
  弾かれるため。
- `stampField` を `selfUpdate` のどれかに挙げていたら拒否。**順位を書き換えられる**。
- `window.fromField.in` が実在するコレクションで、`field` がそこの保存フィールドであること。
- `window.fromField.ref` が、このコレクションの `ref` フィールドか文字列フィールドであること。

## 実装順と deploy 順

`assignee` の計画と同じく **ルール → core 公開 → MulmoTerminal**。逆順だと、新しい宣言を載せた
アプリを古いルールが見て `stampField` を検査せず（**順位の偽装が素通り**）、`fromField` も
読まないので窓が効かない。**こちらは安全側に倒れないので、順序の厳守がより重要**。

1. `../mulmoserver` にルールとテストを入れ、**手動 deploy**（CI が無く、deploy 済みかどうかが
   どのリポジトリにも記録されないので、deploy したことを PR に書く）。
2. core に `stampField` / `window.fromField` と検査を入れ、publish。
3. MulmoTerminal で bump、公開フォーム射影と SKILL。

### テスト（`test/rules/`）

- `createdAt` に `request.time` 以外を書いた create が拒否される（**過去・未来の両方**）
- `stampField` を宣言していないコレクションでは従来どおり通る（非退行）
- `selfUpdate` によるキャンセルで `createdAt` が変わらない限り通る / 変えると拒否
- `opensAt` より前の create が拒否され、後の create が通る
- 参照先のクラスが無い / `opensAt` が無いとき拒否（fail closed）
- 同一人物の 2 件目の申込みが `idFrom` で拒否される（既存機構の確認）

## 採らなかった案

- **分散カウンタ / トランザクションで残席を管理** — ルールが件数を見られない以上、不変条件を
  クライアントの善意に預けることになる。8 時の殺到で競合が最大化するのも最悪。
- **席をドキュメントにする**（`class-x_seat-1` … を先に作り、空席を獲得させる）— create-only で
  ルールが本当に強制できるのは魅力だが、**一意性を 2 軸で強制できない**。ドキュメント ID で
  守れるのは「1 席 1 人」か「1 人 1 枠」の片方だけで、両方守るには 2 件を同時に書く必要があり、
  ルールは 1 件ずつしか判断しないので原子性を強制できない。「1 人が 3 席取る」を防げない。
- **Firestore トリガで定員・待機・繰り上げを持つ** — 正しいが、`../mulmoserver/functions/` には
  現在 oauth / push / server しかなく **Firestore トリガが 1 本も無い**（メールも Trigger Email
  拡張任せ）。新しい層を 1 つ増やす判断になる。定員が厳格に効かねばならないアプリが出てきたら
  そのときに。

## 決めていないこと

- **`stampField` と `opensAt` を 1 本の PR にするか分けるか。** 独立しており、`stampField` は
  先着以外にも効くので単独で価値がある。分けるほうがよいと見ている。
- `window.fromField` の宣言の形。上では `{ ref, in, field }` としたが、`in` を `ref` フィールドの
  `to` から取れば冗長さは減る。ただし**レコードの値からパスを組み立てない**という原則との
  兼ね合いを確認すること（`to` はスキーマ側の固定値なので問題ないはず）。
- 定員（8 / 2）をビューの config に置く形で、オーナーが**クラスごとに変えたい**場合どうするか。
  クラスのレコードに `capacity` / `waitlist` を持たせてビューが読むのが素直だが、そうすると
  ルールが知らない数字がレコードに載る（構わないが、SKILL で「これは表示上の定員である」と
  明記が要る）。

## 実装時に決めたこと（2026-08-12）

- **`stampField` と `opensAt` は 1 本にまとめた。** どちらもジムのテンプレート 1 つを
  成立させるために要り、別々に出すとルールの deploy が 2 回になる（手動 deploy なので
  回数が費用）。
- **`window.fromField` のキーは `in` ではなく `collection`。** `in` はルール言語の**演算子**で、
  `w.fromField.in` は構文エラーになる。計画で書いた綴りは使えなかった。
- **`ref` フィールドの `to` から `collection` を推測することはしない。** 宣言に固定で書かせる。
  パスがレコードの値から組み上がらないことが、この機構の安全性の根拠なので、推測を挟むと
  その根拠が 1 段弱くなる。
- **`opensAt` は `number`（epoch millis）に限定し、`datetime` を拒否する。** ルールは
  `request.time.toMillis()`（数値）と比べるので、Timestamp との比較は型エラーになり全拒否に
  なる。動くように見えて 1 件も通らない、この機構で最も分かりにくい失敗なので拒否する。
- **`stampField` は公開フォームの射影に載せるが、入力欄としては描かない。** `createFields` に
  必要（ルールがリスト外のキーを拒否する）でありながら、人が答えるものではない。
  `statusField` と同じ扱い。
- **定員（8 / 2）はクラスのレコードに持たせた。** クラスごとに変えられる。ルールは読まない。
  テンプレートに「これは表示上の定員である」と明記した。
